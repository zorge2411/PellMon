<objective>
Establish a single repo-root `VERSION` file as the one authoritative version number (D-02), reconcile the pre-existing `configure.ac` `0.7.0` vs git tag `v1.0.0` conflict, and make the Docker image actually report that number instead of the `_dev_` fallback.

Purpose: Without this, the published Docker Hub tag and the version the running app reports are two unrelated strings — exactly the support/debugging failure mode RESEARCH.md Pitfall 3 flags. Plans 09-02 and 09-03 both consume `VERSION` as their input, so this plan is Wave 1.

Output: `VERSION`, a reworked `configure.ac` `AC_INIT`, a Dockerfile step that generates `src/Pellmonsrv/version.py`, and a drift-guard test.
</objective>

Reconciled-version rationale (this satisfies D-02's requirement to flag, not silently pick): `configure.ac` says `0.7.0` while the only git tag is `v1.0.0`, and Phases 6-8 shipped real Docker deployments under that tag. `1.0.0` is both the higher number and the one users have actually seen, so it is the baseline; this phase adds a feature (Docker Hub publishing), which under the Conventional Commits rules locked in D-03 is a minor bump. Note in a one-line `dnl` comment directly above `AC_INIT` that the version lives in the repo-root `VERSION` file and that `autoreconf` must therefore be run from the repo root (which `autogen.sh` already does). This is a new Autotools idiom for this repo — no existing `m4_esyscmd` usage exists to copy from.

Change nothing else in `configure.ac`; the `AC_CONFIG_FILES` list, `AM_PATH_PYTHON`, and the `--with-user_srv`/`--with-user_web` options stay exactly as they are.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| repo → Docker build context | `VERSION` crosses into the image build; its contents end up in a generated Python module |
| repo → autoconf m4 expansion | `m4_esyscmd_s([cat VERSION])` executes a shell command at `autoreconf` time |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-09-01 | Tampering | `VERSION` → `m4_esyscmd_s` shell expansion in `configure.ac` | mitigate | The command is the fixed literal `cat VERSION` with no interpolation of file contents into the shell; `tests/test_version_source.py::test_version_file_format` rejects any `VERSION` content that is not three integers, so shell metacharacters cannot reach a command line |
| T-09-02 | Spoofing | Image reports a different version than its registry tag | mitigate | Dockerfile generates `version.py` from the same `VERSION` file that plan 09-03's workflow guard compares against the pushed git tag; the `RUN` step fails the build if substitution produced no version string |
| T-09-03 | Information Disclosure | `COPY VERSION` into the image | accept | `VERSION` is a public three-integer string with no secret content; `.dockerignore` continues to exclude `.git/` and `venv-*/` so no credential material is added to the build context |
| T-09-SC | Tampering | npm/pip/cargo installs | accept | This plan installs no packages — no `requirements.txt`/`requirements-dev.txt` change, no new marketplace action. RESEARCH.md's Package Legitimacy Audit records "not applicable" for this phase |
</threat_model>
