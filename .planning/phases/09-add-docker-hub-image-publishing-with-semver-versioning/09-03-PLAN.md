  <action>
Create `.github/workflows/publish.yml` alongside `ci.yml` — do not modify or absorb `ci.yml`, which keeps running the pytest/import-check on every push and PR.

Use the exact trigger, job id, runner, permissions block, action pins, platform string and image tags given in the `<interfaces>` block. Give every step a `name:` field, matching `ci.yml`'s convention so the Actions UI stays readable. Use spaces only — no tab characters anywhere (the tests assert this).

Step order:
1. `Checkout repository` — `actions/checkout@v4`.
2. `Read version from VERSION file` — a `run:` step that reads the repo-root `VERSION` file, strips whitespace, and writes it to `$GITHUB_OUTPUT` under an id such as `version`. Give the step an `id:` so later steps can reference the output.
3. `Verify tag matches VERSION file` — a `run:` step that fails the job (exit 1) unless `v<VERSION>` equals `github.ref_name`, printing both values in the failure message. This is the T-09-02 mitigation: it makes it impossible to publish an image whose registry tag disagrees with the version the app reports from `src/Pellmonsrv/version.py`. Place this BEFORE the login step so a mismatch never authenticates to Docker Hub.
4. `Set up QEMU` — `docker/setup-qemu-action@v4` (registers binfmt handlers so the arm/v7 leg can execute).
5. `Set up Docker Buildx` — `docker/setup-buildx-action@v4`.
6. `Log in to Docker Hub` — `docker/login-action@v4` with `username: ${{ secrets.DOCKERHUB_USERNAME }}` and `password: ${{ secrets.DOCKERHUB_TOKEN }}`. The secrets must appear ONLY as `with:` inputs to this action — never inside a `run:` block, never echoed, never passed to a raw `docker login -p`. `docker/login-action` masks the credential in logs by design; a shell `docker login -p` does not.
7. `Build and push multi-arch image` — `docker/build-push-action@v7` with `context: .`, `platforms: linux/amd64,linux/arm/v7`, `push: true`, and a `tags:` block listing `peterscholer74/pellmon:latest` and `peterscholer74/pellmon:<version-output>`. Add `cache-from: type=gha` and `cache-to: type=gha,mode=max` — this is the RESEARCH.md Pitfall 1 mitigation, so repeat arm/v7 builds reuse layers instead of recompiling C extensions under emulation every release. Set `provenance: false` so the published manifest list contains exactly the two requested platforms and no attestation-only `unknown/unknown` entries that confuse `docker manifest inspect` during plan 09-04's verification.

Set `timeout-minutes: 120` on the job. Justification, stated in a YAML comment directly above it: the arm/v7 leg compiles `gcc`/`python3-dev`-dependent wheels under QEMU emulation, which RESEARCH.md Pitfall 1 measures at 5-20x native; the default GitHub 6-hour limit would let a hung build burn the account's minutes, and a value far below 120 risks cancelling a legitimate cold-cache first release.

Add a short YAML header comment stating that this workflow publishes to Docker Hub on tag push only, that credentials come from repository secrets, and that `docker-compose.yml`'s local `build:` / `pull_policy: never` path is unaffected (D-05).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| git ref → workflow trigger | Anyone with push access can create a tag; that tag is the sole authorization to publish |
| GitHub Actions secret store → runner process | The Docker Hub PAT is decrypted into the runner for the duration of the job |
| runner → Docker Hub registry | An authenticated write to a public artifact consumers will `docker pull` |
| GitHub Actions marketplace → runner | Third-party action code executes with access to the job's secrets |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-09-07 | Tampering | Publish trigger scope | mitigate | `on: push: tags: ['v*.*.*']` only — no `pull_request:`, `branches:` or `schedule:`, so unreviewed PR-branch code can never be tagged `:latest`. Enforced by `test_publish_triggers_on_tags_only` |
| T-09-08 | Tampering (supply chain) | `docker/*` and `actions/checkout` marketplace actions | mitigate | Every action pinned to an explicit major version tag (`@v4`/`@v7`) sourced from the official Docker documentation via 09-RESEARCH.md; `@main`/`@master`/`@latest` are absent and asserted absent by `test_all_actions_are_version_pinned`. Residual risk: a major-version tag can be re-pointed by its publisher — accepted, since all four actions are published by the official `docker` GitHub organization and SHA-pinning would block routine security patches |
| T-09-09 | Information Disclosure | Docker Hub PAT in workflow logs | mitigate | The PAT is referenced only as a `with: password:` input to `docker/login-action@v4`, which masks it; no `run:` shell line may reference `DOCKERHUB_*`, enforced by `test_credentials_come_only_from_secrets`. `job.permissions` is narrowed to `contents: read` so a compromised step cannot write to the repo |
| T-09-02 | Spoofing | Published image tag vs. app-reported version | mitigate | The tag-vs-`VERSION` guard step runs before login and exits nonzero on mismatch; ordering enforced by `test_tag_matches_version_guard_precedes_login` |
| T-09-10 | Denial of Service | QEMU-emulated arm/v7 build consuming Actions minutes | mitigate | `timeout-minutes: 120` bounds a hung build well below the 6-hour default; `cache-from`/`cache-to: type=gha` avoids recompiling C extensions under emulation on every release |
| T-09-SC | Tampering | npm/pip/cargo installs | accept | This plan installs no packages — the four Docker actions are marketplace references pinned by version tag, not package-manager installs. RESEARCH.md's Package Legitimacy Audit records "not applicable" for this phase |
</threat_model>
