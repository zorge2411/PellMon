    "How a release happens" — describe the actual `publish` job flow as implemented in `ci.yml`: push
    to `master` -> `test` job -> `publish` job -> `tools/version_bump.py decide` -> on a bump, commit

    containing the substring `BREAKING CHANGE` (case-sensitive, anywhere in the message) -> major; a
    line starting `feat:` or `feat(scope):` -> minor; a line starting `fix:` or `fix(scope):` ->
    patch; anything else -> no release at all (no commit, no tag, no image push — a clean no-op, not a
    failure). Note the priority is existence-based, not chronological.

    "Previewing the next version locally" — `python tools/version_bump.py decide --dry-run` and
    `python tools/version_bump.py decide --dry-run --type minor`, stating that `--dry-run` writes
    nothing.

    "Known deviations from the reference algorithm" — two bullets: (a) the reference
    `increment-version.ps1` never commits `VERSION` ("that's the caller's job") whereas this CI does
    commit and tag it (D-04); (b) the reference `publish.ps1` pushed `:latest` and `:{version}` as two
    independent `docker push` calls and failed fast before attempting the second, whereas
    `docker/build-push-action`/buildx pushes all tags as one atomic multi-platform manifest operation,
    so per-tag failure isolation does not exist — an accepted consequence of the multi-arch
    requirement (D-02), not an oversight.

    "Troubleshooting" — the four named failure modes with their signatures: 403 / `protected branch
