<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GitHub Actions runner -> repo (master branch) | The workflow's GITHUB_TOKEN writes a commit and a tag back into the protected mainline |
| GitHub Actions runner -> Docker Hub | Repo secrets authenticate a push of an image consumed by production Raspberry Pi deployments |
| Commit message content -> workflow shell | Attacker-influenceable commit text flows into a run: step's context |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-09-01 | Elevation of Privilege | `publish` job GITHUB_TOKEN | mitigate | `permissions: contents: write` declared at the `publish` job level only; the `test` job keeps its default read-only token. Asserted by `test_publish_workflow_permissions_and_skip_ci` |
| T-09-02 | Information Disclosure | Docker Hub credentials | mitigate | Credentials are passed only as `with: username/password` inputs to `docker/login-action`; `test_publish_workflow_multiarch_and_tags` asserts `docker login -p` and `--password ` never appear in a `run:` step |
| T-09-04 | Tampering | Release tags | mitigate | `git tag -a` is used without `--force`; the test asserts `--force` and `git tag -f` are absent, so a re-run on an existing `v{version}` fails loudly instead of rewriting a shipped release |
| T-09-05 | Tampering | Third-party GitHub Actions supply chain | mitigate | All four `docker/*` actions pinned to an explicit major-version tag verified against the action's current release at implementation time; `@main`/`@master` floating refs forbidden and grep-asserted |
| T-09-06 | Spoofing | Publish trigger | mitigate | `if: github.event_name == 'push' && github.ref == 'refs/heads/master'` plus `needs: test` — a pull_request from a fork can never reach the publish job or its secrets |
| T-09-07 | Denial of Service | Workflow self-trigger loop | mitigate | The bot's bump commit carries the `[skip ci]` marker (D-04) and a plain `push:` trigger is used rather than `workflow_run`; second-layer protection is that a `chore:` commit body matches none of the three bump rules, so any stray re-run no-ops |
| T-09-SC | Tampering | npm/pip/cargo installs | accept | No packages installed by this plan; the only new dependencies are first-party Docker-org GitHub Actions, which 09-RESEARCH.md's Package Legitimacy Audit documents as out of scope for the registry slopcheck protocol |
</threat_model>
