<interfaces>
<!-- Locked contract for scripts/bump-version.sh. Plan 09-04's docs and the human
     release procedure both depend on these exact names and exit codes. -->

Invocation:  `scripts/bump-version.sh [--dry-run]`
Working dir: repo root (the script must resolve the repo root from its own location, not from `$PWD`)

Exit codes:
  0  — VERSION was bumped, OR no release-triggering commits were found (no-op)
  1  — VERSION file missing, or not exactly three dot-separated integers, or not inside a git work tree

Stdout contract (plan 09-04's DOCKER.md release section quotes these):
  - `Current version: X.Y.Z`
  - `Bump type: major|minor|patch`
  - `New version: X.Y.Z`
  - on no-op: `No release-triggering commits since <tag-or-'repo start'>.`
  - after a real bump, the literal follow-up commands for the human to run:
      `git add VERSION`
      `git commit -m "chore(release): X.Y.Z"`
      `git tag -a vX.Y.Z -m "vX.Y.Z"`
      `git push origin master --follow-tags`   (or `git push origin vX.Y.Z`)

Hard prohibition: the script itself must never invoke `git add`, `git commit`, `git tag` or
`git push`. It only ever READS git history (`git describe`, `git log`, `git rev-parse`).

Bump priority order (locked by docs/versioning-and-publish-reference.md step 2c —
first match wins, evaluated against ALL commit message text since the last tag):
  1. substring `BREAKING CHANGE` (case-sensitive, anywhere)  → major  (X+1.0.0)
  2. regex `^feat(\(.+\))?:` at start of any line             → minor  (X.Y+1.0)
  3. regex `^fix(\(.+\))?:` at start of any line              → patch  (X.Y.Z+1)
  4. otherwise                                                → no-op, exit 0
No handling of `docs:`/`chore:`/other prefixes — the reference doc is deliberately minimal
and must be matched exactly, not extended.
</interfaces>

Step 3 — classify the bump using the RESEARCH.md `Pattern 2` if/elif chain verbatim (`grep -q "BREAKING CHANGE"`, then `grep -qE '^feat(\(.+\))?:'`, then `grep -qE '^fix(\(.+\))?:'`). Step 4 — compute the new version from `major`/`minor`/`patch` per the priority table in the `<interfaces>` block, and echo `Current version:`, `Bump type:` and `New version:` exactly as specified there.

Step 5 — write the new version to `VERSION` (single line, trailing newline, no `v` prefix) unless `--dry-run` was passed, in which case echo that no file was written. Then print the four follow-up git commands from the `<interfaces>` contract as plain text for the human to copy.

Under no circumstances call `git add`, `git commit`, `git tag` or `git push` — D-03 keeps tag creation and pushing human-in-the-loop, matching the reference doc's own explicit design choice.

Do not create a `.py2bak` counterpart.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| git history → bump script | Untrusted commit-message text from any contributor is matched by `grep` inside the script |
| VERSION file → bump script arithmetic | File contents become shell variables used in arithmetic and written back |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-09-04 | Tampering | `scripts/bump-version.sh` commit-message matching | mitigate | Commit text is only ever piped into `grep -q`/`grep -qE` via stdin, never `eval`'d and never interpolated into a command line; the classification result is one of three fixed literals (`major`/`minor`/`patch`) |
| T-09-05 | Tampering | `VERSION` contents used in arithmetic | mitigate | Step 1's precondition block rejects anything that is not exactly three integers before any arithmetic runs; four malformed-input tests in Task 2 pin the nonzero exit |

| T-09-SC | Tampering | npm/pip/cargo installs | accept | This plan installs no packages. RESEARCH.md's Package Legitimacy Audit records "not applicable" for this phase — no `requirements*.txt` change |
