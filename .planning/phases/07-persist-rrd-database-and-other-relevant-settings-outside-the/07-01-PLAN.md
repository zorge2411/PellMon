<objective>
Move PellMon's persistent data out of Docker named volumes and into a host folder the user
controls, and make ownership correct automatically on every start.

Purpose: `docker compose down -v`, a Docker reinstall or a container recreation must not be able
to destroy the RRD database or the settings database (D-01, D-02, D-03).
Output: reworked `docker-compose.yml` (bind mounts + `pellmon-init` one-shot service),
`.env.example` documentation, `.gitignore`/`.dockerignore` entries, and text regression tests.
</objective>

Compose facts the executor must not break (pinned by existing tests in
`tests/test_ci_docker_config.py`):
- `pellmonsrv` health check uses `dbus-send --bus=unix:path=...`; the daemon command uses
  `dbus-daemon --session --address=unix:path=...`. Never replace one form with the other.
- Both services must keep `XDG_CACHE_HOME=/tmp` and `start_period` >= 60s.
- `group_add: - "${SERIAL_GID:-20}"` must stay on `pellmonsrv`.
- `_service_block()` in the test file splits services with the regex
  `^  <name>:\r?\n(.*?)(?=^  \S|^\S|\Z)`, so a new service key must be indented exactly two
  spaces and contain no lines starting at column 0 or 2 inside it.
- The file currently mounts `./config/pellmon.conf:/etc/pellmon/pellmon.conf:ro` (both services)
  and `./config/conf.d:/etc/pellmon/conf.d:ro` (both services).

Decided defaults for this phase (research Open Questions, now settled):
- `config/conf.d` is chowned to 999:999 by the init step (NOT `a+rw`); host-side edits of those
  files afterwards need `sudo`. Documented in plan 07-05.
- `pellmonsrv` gets `PELLMON_REQUIRE_DATADIR=1` in its `environment:` block; plan 07-02
  implements the hard-exit behaviour behind that variable.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| host filesystem → init container (root) | The init container gets root and write access to three host paths through bind mounts |
| host filesystem → git/Docker build context | Runtime data (settings DB with future MQTT secrets, backups) must not leak into commits or images |
| container → container (srv writes, web reads) | The web process must not be able to corrupt the RRD or settings DB |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-01 | Elevation of Privilege | `pellmon-init` running as `user: root` | mitigate | The service mounts exactly three paths (`.../data`, `.../logs`, `./config/conf.d`), runs a fixed `sh -c` with literal paths (no variable expansion inside the container, no user input), and exits; `restart: "no"` keeps it one-shot |
| T-07-02 | Tampering | `chown -R` following symlinks planted under the data folder | mitigate | Targets are directories created by the same step; `chown -R` is limited to the three mounted trees and never runs on `/`, `./config` or `pellmon.conf`. A hostile symlink inside those trees implies an already-compromised host |
| T-07-03 | Information Disclosure | data folder inside the repo and build context | mitigate | `pellmon-data/` added to `.gitignore` (D-05) and `.dockerignore`; `.dockerignore` also keeps `config/` out of the image |
| T-07-04 | Tampering | `pellmonweb` writing to the RRD / settings DB | mitigate | Data mount stays `:ro` for `pellmonweb` (D-04); only `conf.d` is writable there |
| T-07-05 | Tampering | web container rewriting `pellmon.conf` (password hashes) | mitigate | `./config/pellmon.conf` stays `:ro` in both services (D-08) |
| T-07-06 | Denial of Service | world-writable `conf.d` on a shared Pi | mitigate | Ownership is set with `chown -R 999:999`, never `chmod a+rw`; directories stay 755 |
| T-07-07 | Repudiation | data silently lost by `docker compose down -v` | mitigate | Only `pellmon-run` remains a named volume (D-03); data is a bind mount |
| T-07-SC | Tampering | npm/pip/cargo installs | accept | No package installs in this plan; 07-RESEARCH.md Package Legitimacy Audit records zero added packages |
</threat_model>
