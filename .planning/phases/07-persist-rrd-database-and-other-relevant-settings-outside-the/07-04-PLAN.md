<interfaces>
Effective configuration (verified in the repo):
- `config/pellmon.conf` `[conf] database = /var/lib/pellmon/pellmon.rrd`, but every `*.conf` under
  `[conf] config_dir` is read afterwards and overrides it: `config/conf.d/database.conf` sets
  `database = /var/lib/pellmon/rrd.db`. The effective RRD file is therefore `rrd.db`. The tool MUST
  compute this the same way (configparser with `interpolation=None`, `optionxform=str`, read
  `pellmon.conf` then every `*.conf` found by `os.walk(<config dir>)` in sorted order) and must
  never hard-code a filename.

- **Host vs container paths (this is the trap).** `[conf] config_dir = /etc/pellmon/conf.d` is the
  path *inside* the container. The backup tool runs on the HOST, where that directory does not
  exist; walking it finds nothing, `conf.d/database.conf` is never read, and the tool would fall
  back to the stale `pellmon.rrd` value from `pellmon.conf`. Therefore:
  * The conf.d overlay is read from a **host** directory: `--host-config-dir`, defaulting to
    `<dirname(--config)>/conf.d` (i.e. `./config/conf.d` for the default `./config/pellmon.conf`).
    In the repo layout, `./config/conf.d` is exactly what compose bind-mounts onto
    `/etc/pellmon/conf.d`, so the two are the same files.
  * If the configured `config_dir` *does* exist on the host (a real Linux install, or `--local`
    against installed paths), use it; otherwise use the host fallback above. Log at debug level
    which directory was used.
  * The resulting `database`/`settings_db` values stay exactly as written in the config — they are
    **container** paths in docker mode and are passed unchanged to `docker compose exec`; they are
    host paths in `--local` mode. Only the *location of the conf.d files* is remapped, never the
    values read out of them.
  * If no `[conf] database` value is found in either file, fail with
    `no 'database' value found in <conf_file> or <config dir used>` and exit 1. Never guess a
    filename.
- `[conf] settings_db` is normally absent; the daemon then uses
  `dirname(<database>)/pellmon_settings.db`.
- Compose (after plan 07-01): service names `pellmonsrv`, `pellmonweb`, `pellmon-init`; data bind
  mount `${PELLMON_DATA_DIR:-./pellmon-data}/data` → `/var/lib/pellmon`; config bind mounts
  `./config/pellmon.conf` → `/etc/pellmon/pellmon.conf` and `./config/conf.d` →
  `/etc/pellmon/conf.d`; the `pellmon:latest` image contains `rrdtool` and `python3` (with stdlib
  `sqlite3`) but NOT the `sqlite3` CLI.
- `Keyval_storage` (`Pellmonsrv.database`, modified by plan 07-02 to chmod 0600) is used by the
  round-trip test to create and read back a settings database — hence the dependency on 07-02.

Style analog: `tools/burner_sim.py` — GPL header block (lines 1-17), one stdlib import per line,
`logger = logging.getLogger('<toolname>')`, `parse_args(argv=None)` / `main(argv=None)` returning an
int, `if __name__ == '__main__': sys.exit(main())`, `%`-formatting, `sys.stderr.write` for errors.
Test loader analog: `tests/test_burner_sim_pty.py` loads `tools/burner_sim.py` with
`importlib.util.spec_from_file_location` (the `tools/` folder is not a package).
