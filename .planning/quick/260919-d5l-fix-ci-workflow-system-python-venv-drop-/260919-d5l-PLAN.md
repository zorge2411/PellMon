<objective>
Fix `.github/workflows/ci.yml` so the CI job on PR zorge2411/PellMon#2 stops failing in
"Install Python dependencies" with `Cannot uninstall pip 24.0 ... installed by debian`.

Root cause: the job sets `PYTHONPATH: /usr/lib/python3/dist-packages:src` at job level, so
actions/setup-python's Python 3.11 sees Debian's distutils-installed pip and tries to
uninstall it on `pip install --upgrade pip`. Separately, setup-python 3.11 is the wrong
interpreter for `python3-dbus`/`python3-gi`/`python3-rrdtool`, which apt installs only for
the system python3.

Fix: drop `actions/setup-python`, run on the runner's system `python3`, create a venv with
`--system-site-packages` (so apt-provided dbus/gi/rrdtool remain importable), install
requirements plus test deps into that venv, drop the pip self-upgrade, and set
`PYTHONPATH: src` only on the steps that run tests.

Purpose: unblock CI for the python3-migration branch.
Output: rewritten workflow, updated workflow-integrity test, green CI on PR #2.
</objective>

Edit `.github/workflows/ci.yml` in place. Keep the `name: CI`, the `on:` triggers
(push + pull_request on master and python3-migration), the job id `test`, its
`name:`, and `runs-on: ubuntu-latest` exactly as they are.

Changes:
1. Delete the job-level `env:` block containing
   `PYTHONPATH: /usr/lib/python3/dist-packages:src`. Nothing at job level may set
   PYTHONPATH — that leak is what makes pip see Debian's pip 24.0.
2. Delete the `Set up Python 3.11` step (`actions/setup-python@v5`) entirely. Tests
   run on the runner's system `python3` so that apt-installed `dbus`, `gi` and
   `rrdtool` bindings are importable.
3. Keep the `Install Linux system packages` step unchanged, but add `python3-venv`
   to the apt package list (the venv creation in the next step depends on it; on
   ubuntu-latest it is usually present but must not be assumed).
4. Replace the `Install Python dependencies` step body with, in order:
   - `python3 -m venv --system-site-packages "$RUNNER_TEMP/venv"`
   - `echo "$RUNNER_TEMP/venv/bin" >> "$GITHUB_PATH"` so subsequent steps get the
     venv's `python`/`pip` first on PATH (GitHub Actions gives each step a fresh
     shell, so activating with `source` would not persist).
   - Do NOT run `python -m pip install --upgrade pip` or any other pip self-upgrade.
     Note the reason in a YAML comment on that step: upgrading pip is what triggered
     `Cannot uninstall pip 24.0 ... installed by debian`.
   - Split the actual installs into a separate step (named e.g.
     `Install Python dependencies`) that runs after the PATH export step, since
     `GITHUB_PATH` only takes effect in *later* steps. That step runs
     `pip install -r requirements.txt` then
     `pip install pytest pytest-mock pytest-socket`. Add
     `python -c "import sys; print(sys.executable)"` (or `pip --version`) as the
     first line of that step so the log proves the venv interpreter is in use.
   - Name the venv-creation step something explicit such as
     `Create virtualenv with system site packages`.
5. Add `env: PYTHONPATH: src` at STEP level on both the `Run import tests` step and
   the `Run test suite` step. No other step gets PYTHONPATH.
6. Add a step (after the installs, before the tests) that asserts the system-site
   bridge works: `python -c "import dbus, gi, rrdtool; print('system bindings OK')"`.
   If this fails, the venv is not seeing apt packages and the rest is meaningless.

Keep the file tab-free (the integrity test rejects any tab character) and keep the
literal strings `test-imports.py` and `pytest tests/` present.
